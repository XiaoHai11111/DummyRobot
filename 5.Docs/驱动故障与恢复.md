# F1 驱动故障、F4 恢复与统一运动指令

适用于主工程 `2.Firmware/Ctrl-Step-Driver-STM32F1-fw`、`2.Firmware/Core-STM32F4-fw` 和 DummyWeb。F1 与 F4 必须配套升级，六个 F1 都要更新。DummyPeak 子模块内仅同步了旧实时指令到 `>` 的迁移，其存档 F4 工程没有本次故障协议升级。

## 已定位的问题

- F4 的 CAN 发送原来无限等待 TX 信号量，HAL 发送失败、错误和中止没有可靠释放路径。现在发送过程在任务间串行化，信号量最多等待 2 个 RTOS tick，邮箱最多等待 2 ms，并在每条退出路径释放；邮箱超时会取消待发报文。不会在 CAN 错误回调重发旧目标。
- F1 的 CAN 发送邮箱满或接收失败原来进入 `Error_Handler()`，可以把整个驱动卡住。现在丢弃本次反馈，让下次轮询重试。两端 CAN1 开启自动 bus-off 恢复和硬件自动重发，仲裁失败后由硬件重试；F4 停止时逐轴查询，减少六个 F1 同时争用广播回复。F4 发送等待仍有上限，邮箱超时会中止待发帧。
- F4 的两个 CAN 原来都使用过滤器 bank 0，并把共享过滤器分界设为 0。现在 CAN1 使用 bank 0、CAN2 使用 bank 14，共享分界固定为 14，避免 CAN2 初始化改变 CAN1 的过滤器归属。
- F4 的 `CAN1_RX0_IRQHandler` 原来只读取消息就提前返回，跳过 `HAL_CAN_IRQHandler`。FIFO FULL/OVERRUN 通知已启用，但粘滞标志没有清除，可能形成持续中断，导致 OLED/USB/RTOS 任务停滞。现在使用标准 HAL 中断处理，同时处理消息、满和溢出标志。
- 反馈超时检查现在先读取中断更新的接收时间，再读取当前时钟。原先先缓存当前时钟，期间若 CAN 中断记录了下一毫秒的时间，做无符号减法会错误得到极大时间差，误锁存掉线。
- 原位置回复只有 `finished`，F4 无法知道未完成是过载、堵转还是通信失联。新增版本标记、驱动状态和故障位；不依赖 F1 故障后还能发送“完成”回复。
- 原队列把 `std::string::c_str()` 当作固定 64 字节消息读取，短命令会越界读取，长命令也未保证结尾。现在使用初始化过的定长消息（最多 127 字符），携带回复通道和代次。停止、失能、切换模式或 INT 新目标会使旧队列项失效。
- 原 `MoveJ` 在目标等于当前位置时除以零；速度公式也混用了关节角和电机转速。现在 `time = 最大关节角差 / 关节速度`，`motor_rps = 关节角差 × 减速比 / (360 × time)`。例如 J2/J3 为 30:1，速度 30 的上限从约 36°/s 修正为 30°/s。没有宣称六轴的加减速段严格同步或实现了完整 MoveL 直线插补。
- F1 的 DCE/PID 原积分器只限制 I 自身，没有考虑 P+I+D 已经饱和。现在在会加剧输出饱和时暂停积分，允许反向退积分并保留正常负载积分。堵转计时要求连续满足条件；恢复速度后清零。位置完成还要求实测误差及速度进入容差。运行时调整加速度也会同步更新规划器的低速制动阈值。

## 状态与停止策略

F1 的 OVERLOAD 是**控制器计算输出电流持续达到配置上限约 1 s**，不是 ADC 实测过流或温度报警。用户当前的 42×34 mm 两相四线电机、3 A 上限、DCE `1000/80/300/250` 会保留，不自动修改 EEPROM 参数，也不放宽检测时间或关闭保护。

F1 在首次过载后把目标改成自己的实测位置，锁存故障，并拒绝普通运动目标；保持模式继续提供位置保持力矩。已有堵转保护在启用且触发时仍会关闭输出。编码器未校准仍不能闭环。电源、过温和驱动芯片内部保护没有独立传感反馈，不能由此协议诊断，掉线只能作为通信故障报告。

F4 每个控制周期检查六轴状态；反馈超过 **250 ms** 未更新、F1 报告故障、版本不兼容或使能后驱动意外 STOP，都会锁存对应轴故障，清队列，停止继续发旧目标，向驱动请求保持。上电未收到反馈有 1 s 初始化宽限；宽限期间也不允许在六轴状态未就绪时使能。顺序运动的等待也有上限：至少 30 s，随预计运动时间延长，最多 10 min。

`!STOP` 与故障暂停保留能够响应的关节的位置保持；**F4 的 enabled=0 表示不再接受运动，不代表所有电机已经断电**。`!DISABLE` 和 `!CLEARFAULT` 会使关节驱动停止输出。重力轴在失能、堵转或电源故障时可能下坠，清错/刷写前须支撑好机械臂。这些软件命令不能代替实体急停或机械制动。

## ASCII 命令（USB 与 UART4 相同）

```text
#GETSTATUS
oks enabled mode fault_mask f1 f2 f3 f4 f5 f6
```

`fault_mask` 的 bit0–bit5 对应 J1–J6；`f1`–`f6` 是各轴锁存故障位的十进制组合：

| 位值 | 含义 |
|---|---|
| 1 | F1 过载（计算电流持续饱和） |
| 2 | F1 堵转 |
| 4 | 编码器未校准 |
| 8 | CAN 位置反馈超时 |
| 16 | F1 不支持本次状态协议 |
| 32 | 运动等待超时 |
| 64 | F4 使能超过 100 ms 后驱动仍 STOP，可能未使能或发生重启 |
| 128 | F1 控制循环连续超预算，本地请求保持并锁存 |

例如 `oks 0 2 2 0 1 0 0 0 0` 表示 F4 已暂停、INT 模式、J2 过载。OLED 的旧显示 `FAULT J:25` 是十六进制轴掩码 `0x25`，即 J1/J3/J6；`J:24` 是 J3/J6。不是十进制错误码，也不直接表示过载。ASCII 状态里的同一掩码使用十进制，分别为 37 和 36。

新版 OLED 显示 `FAULT 0x24 J3:08`，每 1.5 s 轮换一个故障轴；`J3:08` 是该轴故障位的十六进制值，下一行显示主要原因，如 `CAN TIMEOUT`、`OVERLOAD`、`STALL`。多个原因并存时看完整位值，或用 DummyWeb 查看中文原因。关节/TCP 位置在失联时是最后一次收到的值，必须结合状态判断是否新鲜。

恢复流程：

1. 查询 `#GETSTATUS`，排除机械卡滞、过大负载或通信故障，支撑重力轴。
2. 若仍处于使能状态，先 `!STOP`。发送 `!CLEARFAULT`（或 DummyWeb 的“清除故障”）。该操作会停止驱动、清积分/故障计时、丢弃旧目标，并等待六轴新反馈确认；最多等待 500 ms。成功回复 `Faults cleared ok`，失败回复 `error ...`。未校准、掉线和旧固件不能通过清错绕过。
3. 再次查询状态应为 `oks 0 ... 0 0 0 0 0 0 0`。清错不会自动使能。
4. 确认实测位置合理，`!START`，然后发送一个新的低速目标。没有旧队列重放。若 F1 发生掉电/重启，电机多圈位置可能已丢失，须先重新确认实际零位，不能仅靠清错恢复坐标。

统一运动命令：

```text
#CMDMODE 2
>j1,j2,j3,j4,j5,j6[,speed[,gripper_angle[,gripper_current]]]
@x,y,z,a,b,c[,speed]
```

- 模式 1：顺序目标点；模式 2：可中断目标点（INT，最新待执行目标覆盖旧目标）。模式 3 仍是未完善的轨迹模式；模式 4 为电机调试，不接收 `>`/`@` 队列运动。
- 关节速度为 `0 < speed <= 100` °/s；夹爪角 `0–45`°、电流 `0–1`。拒绝非法参数、NaN/Inf、超长命令和队列满；成功入队回复 `0–16` 剩余容量。随后 `ok` 表示已应用目标（INT）或等待结束（SEQ），不能把 INT 的 `ok` 当作到位信号。
- 旧实时前缀已删除。DummyWeb、DummyGraspnet、ESP32 转发和 DummyPeak 的发送/SD 记录已改用 `>`。设备 SD 卡上已有的旧动作文件需要转换或重新录制；仓库中的二进制上位机也无法直接修改其内部协议。
- USB、UART4 使用同一入口；各自的流解析缓冲区独立；回复只发送给来源通道。UART5 保持为外设预留入口。
- DummyWeb 使能和滑块动作使用模式 2，默认速度保留配置中的 30°/s；手动指令可显式选择模式 1。模式设置现在有确认回包。

## OLED 停刷与 USB Write timeout

2026-11-17 的 ARM Release 栈检查发现：此前新增状态/恢复分支后，模板 `Respond` 被内联，`OnRobotAsciiCmd` 单函数栈帧达到 **2184 B**，超过 USB/UART 任务原来的 **2000 B**，尚未计入上层解析和 libc 格式化调用。这是确定的栈越界风险，能够导致 USB 接收不再重新挂起、任务内存损坏以及 OLED 停刷；尚无实机调试器记录证明用户每次停机均来自这一处。

项目内已有 `cmake-build-debug` 配置为 Debug；其现有 ELF 中该入口帧是 136 B，不能把 Release 的 2184 B 直接当作该 Debug 固件的停机证据。结合“所有 F1 已更新、OLED 起初刷新随后停住、USB 状态查询也写入超时”，CAN FIFO 标志未清除造成中断持续触发是另一个更直接的候选原因。此次两处都修复，最终仍需实机验证。

修复将 `Respond` 改为禁止内联的普通格式化函数（本次 ARM Release 测得入口 **96 B**，回复函数 **180 B**），USB/UART 栈容量均为 **4096 B**。UART 使用静态 SRAM 栈；USB 在后续通信回归排查中恢复原动态分配方式，使用 CCM 的 RTOS 堆。CMake 对 ASCII 两个源文件启用 `-Werror=stack-usage=512`，防止单函数帧再次膨胀；该检查不是完整调用链栈证明。

DummyWeb 连接时现在先发送只读 `#GETSTATUS`，收到有效回包后才报告连接成功。写入超时、短写、读取异常或回包超时会关闭连接并指出失败命令，不自动重发运动。去掉可能无限等待的 `flush()/tcdrain()`，使用有写入超时的 `write()` 和限时固件应答。关闭串口只代表通信不可用，不代表实体机械臂已失能。

更新本次 F4 和全部 F1 后，重新启动 DummyWeb 服务、重新上电，在未使能时先观察 OLED 持续刷新并确认 `#GETSTATUS`、关节/TCP 遥测可正常返回。若仍有故障，记录轮换显示的轴号、十六进制位值和原因；若仍停刷，记录停刷前最后显示以及是否在连接前就发生，再通过 SWD 检查 HardFault/任务栈。不能用加大网页超时来修复主控停机。

## OLED 正常但 USB 握手仍失败：回归定位版

用户确认旧固件 USB 正常，新固件 OLED 已恢复 `[INT] ======` 并持续刷新，但 DummyWeb 仍出现写入超时或 `#GETSTATUS` 无回包；设备描述为 `REF 1.0 CDC Interface`，与本项目 USB 描述符一致。这应按本轮修改后的通信回归排查，不能据此归因于电机过载、端口选错或物理连接。

本版将 USB 工作任务恢复为原动态分配方式（保留 4096 B 栈），`Respond` 恢复原有的正文、CRLF 分开发送（保留独立函数和长度限制）。这些是用于排除改动影响的回退，尚没有实机结果证明哪处导致了故障。没有把本轮阅读时发现的其他旧 USB 初始化问题混入此验证版。

屏幕顶部改为 USB 诊断，位置和 INT/故障显示仍保留：

```text
U3 S1 R002 P002 T004
Q004 E000 FPS:25
```

- `U`：USB 设备状态，1=默认、2=已分配地址、3=已配置、4=挂起。
- `S`：USB 工作任务已进入运行时为 1。
- `R`：CDC 收到的 USB 包数；`P`：工作任务处理完的 CDC 包数。一次命令可以跨包，多条命令也可能在同一包里。
- `T`：CDC IN 传输完成次数；`Q`：所有 USB 成功提交发送的包数；`E`：发送接口返回失败次数。计数累计且只显示末三位。
- 点击连接前后比较：`R` 不增长说明尚未走到 CDC 数据回调；`R` 增长而 `P` 不增长说明卡在任务/解析路径；`P`、`Q` 增长但 `T` 不增长说明应重点看 IN 完成和主机读取。具体异常还需结合 `U/S/E`。

本轮只涉及 F4，F1 不需要重刷。重新编译/刷写 F4 后，保持未使能，点击一次连接；若仍失败，记录顶部两行在连接前后的值和网页错误。真实 USB 工作任务、ASCII 解析/状态回复、分包及连续多命令的主机测试已经补上；RTOS 和 CDC 硬件收发在该测试里仍是替身，所以测试通过不等于实体串口已恢复。

## 已定位的 Balloc 断言与 libc 堆修复

用户进一步提供了 `#GETJPOS` 回包中的 `assertion "Balloc succeeded" failed ... mprec.c, line 783`，屏幕为 `U3 S1 R003 P002 T012 / Q012 E000 FPS:13`：CDC 已配置且此前能够发送，第三个包在处理过程中没有返回。该断言来自浮点转十进制所需的 newlib 内存分配；`_exit()` 在当前任务内无限循环，USB 工作任务因而不能重新开启 OUT 接收，之后表现为 Write timeout。

根本的堆边界错误在原 `Core/Src/syscalls.c::_sbrk()`：它用当前 `sp` 作为 libc 堆上限。当前 RTOS 动态任务栈位于 CCM（`0x100...`），而 libc 堆在 SRAM（`0x200...`），`heap_end + increment > sp` 必然成立；前一排查版的静态 USB 栈也位于 `.bss` 中、低于 libc 堆起点，不能作为上限。已有 malloc 空闲块还够用时错误可以潜伏，所以旧版本能够通信并不证明该边界判断正确。本次通信回归暴露了它，先前只扩大任务栈没有处理到这一层。

修复包括：

- 链接脚本定义 `__HeapBase`（`.bss` 之后、8 字节对齐）和 `__HeapLimit`（SRAM 顶部扣除 MSP 保留空间）。新的 `Bsp/memory/newlib_heap.c` 仅按该范围扩展/收缩 libc 堆，并检查溢出、下溢及真实耗尽；不侵占 CCM 的 FreeRTOS 堆和主中断栈。
- 提供可嵌套的 `__malloc_lock/__malloc_unlock`，保存并恢复 PRIMASK。这样也覆盖 USB 枚举中断内的分配；锁内部不调用 RTOS、串口或格式化函数。
- 启用 `configUSE_NEWLIB_REENTRANT`，为各任务隔离 newlib 浮点转换/errno 状态。当前 ARM 工具链的 `_reent` 大小为 288 B；本次重新构建全部依赖该配置的任务控制块。
- DummyWeb 识别运行库断言时立即报告具体断言并关闭连接，不再等到普通回包超时才显示。

主机测试直接编译新的 `_sbrk`，覆盖 CCM 地址低于 SRAM、恰好到上限、真实耗尽、失败后 break 不变、负向收缩、INT_MIN、嵌套锁以及调用前已关中断。F4 Debug/Release 构建均通过。这个测试不模拟 newlib 全部实现和实机调度；另提供 `6.Tests/dummyweb/verify_live.py`，可手动通过 DummyWeb 的真实串口实现连续执行只读遥测。

实机验证记录（2026-11-17）：用户刷入修复后的 F4 并接回数据 USB 后，完成 **200 轮、601 条连续只读查询**，耗时 20.2 s，单轮三个查询最长约 8 ms；随后 **10 次重新打开串口及 30 条查询**均成功。再通过正在运行的 DummyWeb HTTP 后端执行连接和 10 轮状态读取，返回 `connected=true`、`enabled=false`、六轴故障位全零。测试结束时已释放独立测试进程的串口，由 DummyWeb 保持连接。验证过程中没有发送使能、清错或运动命令；带载运动性能不在此次验证范围内。

## 运动回复串行化与 CAN 超时诊断（2026-11-17）

堆修复之后，用户实机运动出现 `收到: ['15ok']`。前一排查版把 `Respond` 恢复为正文、CRLF 两次调用；USB 命令任务发送 `15` 后，队列任务可以抢先发送 `ok`，造成行边界损坏。这是固件回复并发缺陷，不能用网页放宽匹配、接受 `15ok` 或自动重发运动来绕过。

本版修复：

- `Respond` 把正文与 CRLF 放进同一个有界缓冲区，一次提交。
- USB CDC、UART4、UART5 各用静态 RTOS 互斥锁保护整次流写入，包括跨 64 字节包的长回复。DMA/USB 完成信号量仍保护硬件发送缓冲；两层锁用途不同。等待均有上限，不在关中断区内等 USB。
- USB 等待发送令牌超时时立即失败，不越过令牌继续写，也不错误释放别的传输持有的令牌。USB 类重新初始化时归还因断开而收不到完成回调的令牌。
- F4 关节与夹爪的 CAN 命令改用调用栈上的独立报文；原实例级可写 `txHeader/canBuf` 在等待发送锁时可能被另一生产者改写。新增抢占回归测试验证这一点。

此时用户屏幕的 `FAULT 0x1F J5:08` 表示 J1–J5 曾被锁存 CAN 反馈超时，`08` 不是电机过载。实际只读 DummyWeb 状态也返回 `enabled=false, faults=[8,8,8,8,8,0]`。这只能证实超时被记录，不能区分持续失联、反馈已经恢复或误判；也不能证明发送缓冲竞争就是这次超时的原因。本版保留 250 ms 门限及故障锁存，不通过放宽门限掩盖问题。

新增只读诊断（所有数值为十进制；可在新版 DummyWeb 指令框输入）：

```text
#GETCAN
okc <RX帧数> <提交TX帧数> <错误计数> <TX中止回调数> <最近HAL错误位> <该错误时ESR寄存器>
#GETDRV 1
okd <轴号> <当前反馈年龄ms> <F1状态> <F1故障位> <F4锁存故障位> <首次超时年龄ms> <有效反馈累计数>
```

## CAN 扩展

CAN 标准帧标识仍为 `(node_id << 7) | command`。

| 报文 | 数据 |
|---|---|
| `0x21/0x22/0x23` 电流/速度/位置回复 | byte0–3：原 float；byte4：finished；byte5：F1 状态；byte6：F1 故障位（1/2/4）；byte7：`0xA1` |
| `0x25` 控制计算耗时查询/回复 | byte0–1：uint16 最近周期；byte2–3：uint16 最大周期；byte4–7：uint32 超预算次数 |
| `0x08` 清除故障 | 无参数；在 20 kHz 控制周期执行，保持 STOP，不擦除配置/编码器校准 |
| `0x09` 保持 | 无参数；捕获驱动实测位置，禁止后到的运动目标，不清故障 |
| `0x01` 使能/失能 | 原 uint32 参数 1/0；显式使能才解除保持后的运动禁入，并以实测位置起步 |

F1 状态编号为 `0 STOP / 1 FINISH / 2 RUNNING / 3 OVERLOAD / 4 STALL / 5 NO_CALIB / 6 CONTROL_OVERRUN`。`0x05/0x06/0x07` 的位置应答同样使用扩展 `0x23`。F4 校验标准数据帧、节点 1–6、DLC、float 和版本；旧 F1 的未定义尾字节不会被直接当作故障位。新 F4 会阻止旧 F1 参与使能，必须配套刷写。

## J2/J3 调整顺序

“保持用力但不再运动”与持续输出饱和相符，但仅凭这一现象无法确定根因。升级后先看实际故障位，不再依据主控无响应猜测。

1. 先用当前 DCE 和 3 A 上限测试，降低速度到 10–20°/s（DummyWeb 修改 `config.json` 后重启服务），逐轴、小范围比较空载与带载。不能仅凭 42 mm 外形确认绕组可长期承受 3 A；核对该电机规格及供电电压。
2. 优先降低加速度。当前模式 2 的默认基准使 J2/J3 分别约为电机 30/60 rev/s²，即关节 360/720°/s²，J3 是 J2 的两倍。可在设置模式/使能后，通过 Fibre 先试 `dummy0.robot.set_joint_acc(10)`，降为原来的三分之一；也可分别设置 `dummy0.robot.joint_2.set_acceleration(10)`、`dummy0.robot.joint_3.set_acceleration(10)`。这些加速度单位是电机 rev/s²，切换命令模式会覆盖运行时设置。
3. 若仍有明显振荡和反复饱和，再单独尝试把 J2/J3 的 `dce_ki` 从 300 降到 150，比较跟随误差及保持下垂；其余增益先不动。此项是待实机验证的调参起点，并非已验证最优值，相关 Fibre 增益设置会写 EEPROM。重力轴不能简单删除积分来消除过载提示。
4. 若低速/低加速度下仍无法静态保持，需要检查减速器摩擦、安装偏心、卡滞、相线、电源压降、负载力矩及电机规格。提高限流或延长过载时间不能解决力矩不足。
